# Code review: Story 3.6 — Eraser, fill & clear via op log

## Summary

Protocol and server fan-out align with acceptance criteria: unified `drawingStrokeSeq`, drawer-only validation mirroring strokes (`NOT_DRAWER`, `WRONG_PHASE`, `BAD_ROOM`), and client replay via `CanvasReplayEvent`. One **critical** client defect affects replay bookkeeping around layout / sizing; clear has an optimistic-update hazard; remaining items are tests and operational assumptions.

**Remediation (2026-04-30):** Resize replay fixed (`DrawingCanvas`: watermark reset only when backing-store dimensions change + layout generation rerun); replay sorts by `seq`; clear is server-authoritative via replay; `BAD_ROOM` canvas-clear integration test added. Historical counts above reflect the original review pass.

### CR-01 — Replay watermark reset without replay pass (`DrawingCanvas.tsx`)

**Severity:** Critical  

**Location:** `applyCanvasSizeAndTransform` forces `remoteWatermarkRef.current = 0` while the replay `useEffect` only depends on `remoteCanvasCommits` and `strokeTransport?.localPlayerId`.

**Problem:**

1. When `canvas.width` / `canvas.height` change, the bitmap is cleared by the browser. Watermark resets to `0`, but the replay effect often **does not re-run**, so the canvas stays **blank** until a new commit arrives.
2. If `applyCanvasSizeAndTransform` runs when bitmap dimensions are unchanged but watermark is still reset to `0`, the bitmap may **keep** existing pixels while the watermark claims nothing has been replayed. The next time `remoteCanvasCommits` grows, the loop reapplies **all** commits from index `0`, risking **duplicate strokes/fills** on top of existing pixels.

**Fix direction:** After resizing (or whenever resetting the watermark), either re-invoke the same replay logic synchronously or bump a `layoutGeneration` / `resizeTick` state included in the replay effect’s dependency array so buffered commits are reapplied exactly once per layout reset.

---

### WR-01 — Optimistic clear without server ack rollback (`DrawingToolbar.tsx` + `MatchDrawingColumn.tsx`)

**Severity:** Warning  

**Location:** Confirm handler sends `drawingCanvasClear`, then immediately calls `onClearConfirmed()` → `clearCanvas()` on the ref.

**Problem:** If the server rejects the command (transient error, race, or future validation), the drawer’s canvas stays cleared locally while peers still see the drawing until another sync path fixes it—violates strict “authoritative server” UX.

**Fix direction:** Clear locally only after success, or on error revert via last-known-good snapshot / request replay (heavier); minimum improvement is surfacing protocol errors for canvas ops and re-fetching or disabling optimistic clear.

---

### WR-02 — Replay orders by buffer index, not `seq` (`DrawingCanvas.tsx`)

**Severity:** Warning  

**Location:** Remote replay consumes `remoteCanvasCommits` in array order; `seq` is not consulted.

**Problem:** Correctness assumes WebSocket delivery and client append order always match monotonic `seq`. Any future merging, reorder, or repair could desync silently.

**Fix direction:** Optional assertion/sort-by-`seq` in dev; production guard that drops or buffers out-of-order events.
